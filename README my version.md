# elastic-security-dns-based-threat-hunting-lab
## Overview
DNS is one of the most useful telemetry sources for SOC threat hunting because almost every networked system depends on DNS to translate domain names into IP addresses. Attackers can also abuse DNS for activities such as command-and-control, beaconing, malware infrastructure discovery, domain generation algorithms, and DNS tunneling.

However, a DNS query by itself is not evidence of compromise. Common applications such as browsers, Windows services, Microsoft applications, security tools, and background processes generate large volumes of legitimate DNS traffic.

This lab focuses on using **Elastic Security and Elastic Defend** to investigate DNS activity generated by a Windows endpoint.

DNS is an important source of SOC telemetry because applications and operating system components continuously use DNS to resolve domains before establishing network connections. Attackers can also abuse DNS for command-and-control, beaconing, domain generation algorithms, and DNS tunneling.

The purpose of this lab is not to treat unusual DNS activity as automatically malicious. Instead, the investigation follows the DNS activity back to the endpoint, user, and originating process wherever telemetry is available.

The investigation also demonstrates an important limitation: a DNS query and a network connection cannot always be directly correlated using a single IP address because DNS responses can contain multiple addresses, addresses can change, and the network event may fall outside the selected time range.

## Lab Objectives

The objectives of this lab are to:

- Understand how DNS telemetry can be used as a source for endpoint threat hunting.
- Identify DNS queries generated by the Windows endpoint and examine their associated timestamps.
- Determine which users and processes are associated with observed DNS requests.
- Analyze DNS query frequency to identify domains that may require additional investigation.
- Distinguish normal operating-system and application DNS activity from activity that warrants further analysis.
- Correlate DNS queries with process IDs and endpoint context where the available telemetry supports it.
- Investigate DNS activity generated by PowerShell without assuming that PowerShell-based activity is malicious.
- Examine repeated DNS queries and evaluate their relevance as potential hunting indicators.
- Attempt to correlate DNS activity with corresponding network connection telemetry.
- Understand why DNS-to-IP-to-network correlation may not always produce a matching network event.
- Practice documenting zero-result searches and telemetry limitations without filling evidence gaps with assumptions.
- Apply an evidence-driven approach when assessing potentially suspicious DNS behavior.
- Clearly distinguish confirmed observations, investigative leads, and behaviors that were not demonstrated.
- Document the investigation timeline using actual Elastic telemetry and observed timestamps.
- Reinforce the principle that a DNS query alone is insufficient to establish compromise, command-and-control, DNS tunneling, or data exfiltration.

## Lab Scenario

A SOC analyst is investigating DNS activity from a Windows endpoint after observing multiple DNS queries during normal system activity. The analyst needs to determine whether the observed DNS behavior is consistent with legitimate applications and system services or whether any activity warrants additional investigation.

The investigation focuses on the following areas:

- Identify the domains being queried by the endpoint.
- Examine how frequently individual domains are requested.
- Correlate DNS queries with the associated user and process.
- Investigate repeated or unusual DNS requests.
- Attempt to correlate DNS activity with network connection telemetry.
- Document telemetry gaps and unsuccessful correlations.

During the investigation, several commonly used domains are observed, including Microsoft, Adobe, Windows Update, `wpad`, and `aka.ms`. Detailed DNS telemetry also shows `dc.services.visualstudio.com` being queried by both `pwsh.exe` under the `Dell` user and `mc-fw-host.exe` under `SYSTEM`.

The analyst then attempts to correlate DNS activity with a destination IP address. The network search returns no matching event within the selected time range. Rather than assuming that the connection did not occur, the analyst treats the result as a correlation limitation and considers factors such as multiple DNS responses, different destination addresses, available network telemetry, and the selected time window.

The investigation should ultimately determine what the available telemetry can actually establish. A DNS query, high query frequency, or PowerShell involvement should not automatically be classified as malicious without supporting evidence.

The scenario therefore emphasizes:

- DNS telemetry analysis
- Query frequency hunting
- Process and user correlation
- DNS-to-network correlation
- Timeline analysis
- Evidence-based assessment
- Clear documentation of unknowns and telemetry limitations

## DNS Telemetry Baseline

The following query was used:

```esql
FROM logs-*
| WHERE dns.question.name IS NOT NULL
| STATS query_count = COUNT() BY dns.question.name
| SORT query_count DESC
```

The query processed:

```text
123 documents
51 groups
```

The most frequently observed domains included:

```text
settings-win.data.microsoft.com
harmonydl.adobe.com
wpad
aka.ms
download.windowsupdate.com
```

The presence of Microsoft, Adobe, and Windows Update related domains demonstrates that the endpoint generates DNS activity from normal software and operating-system components.

## Detailed DNS Investigation

A detailed query was then used:

```esql
FROM logs-*
| WHERE dns.question.name IS NOT NULL
| KEEP @timestamp, host.name, user.name, process.name, process.pid, dns.question.name
| SORT @timestamp DESC
```

This returned:

```text
72 documents
```

One of the observed DNS queries was:

```text
dc.services.visualstudio.com
```

The activity included:

```text
pwsh.exe
PID 6444
User Dell
```

and:

```text
mc-fw-host.exe
PID 5712
User SYSTEM
```

This demonstrates that the same domain can be queried by different processes and users.

## Process Correlation

The observed relationship can be represented as:

```text
DNS Query
    |
    +-- dc.services.visualstudio.com
            |
            +-- pwsh.exe
            |      |
            |      +-- User: Dell
            |
            +-- mc-fw-host.exe
                   |
                   +-- User: SYSTEM
```

The presence of multiple processes querying the same domain does not by itself establish malicious activity.

Additional process and network context would be required before making a security determination.

## Network Correlation Attempt

A destination IP was investigated using:

```esql
FROM logs-*
| WHERE destination.address == "172.217.24.14"
| KEEP @timestamp, host.name, user.name, process.name, process.pid, destination.address, destination.port, network.transport
| SORT @timestamp DESC
```

Result:

```text
0 documents processed
```

Elastic returned no matching network event within the selected time range.

This result was treated as a telemetry finding rather than as evidence that the DNS activity was malicious.

Possible explanations include:

- The resolved IP was not used during the selected time range.
- The domain returned multiple IP addresses.
- The endpoint connected to another resolved address.
- The network event was outside the current time range.
- The available network telemetry did not contain the expected destination.
- The DNS and network events could not be directly correlated from the available fields.

## Key Findings

### Finding 1 — DNS Telemetry Available

The endpoint generated substantial DNS activity.

The frequency query processed:

```text
123 documents
51 unique DNS groups
```

This confirms that DNS telemetry was available for threat hunting.

### Finding 2 — Normal Domains Were Frequently Queried

Examples included:

```text
settings-win.data.microsoft.com
harmonydl.adobe.com
wpad
aka.ms
download.windowsupdate.com
```

These demonstrate that high-frequency DNS activity can originate from legitimate operating-system and application functions.

### Finding 3 — Process Correlation Was Possible

The detailed query showed:

```text
pwsh.exe
```

and:

```text
mc-fw-host.exe
```

generating DNS activity.

This demonstrates the value of correlating:

```text
Domain
+
Process
+
PID
+
User
+
Timestamp
```

### Finding 4 — Direct IP Correlation Failed

The query for:

```text
172.217.24.14
```

returned:

```text
0 documents processed
```

Therefore, no corresponding network event was confirmed for that destination within the selected time range.

## Investigation Assessment

The observed DNS activity does not demonstrate:

```text
DNS tunneling
Command-and-control
Malware execution
Data exfiltration
Domain Generation Algorithm activity
Compromise
```

The investigation did identify useful hunting leads and demonstrated that DNS telemetry can be correlated with endpoint processes.
